Process flow

One AWB, end to end

Eight stages. Each has an owner, and the handover between them is where things go wrong — so the “where” line names the exact screen. A delivery with nothing rejected stops at stage 4.

  1. 01

    SwipeRx sends the TMP batch file

    SwipeRx

    An .xlsx listing every pharmacy order for the day. One SwipeAWB per pharmacy delivery, with its PO lines and koli underneath it. Continuation rows carry only the PO columns — that blank SwipeAWB is what groups them.

    Where: arrives by email, outside this tool.

  2. 02

    Create the orders

    DE / Implant

    Upload the TMP, pick the service, the pickup date and the origin — TMP Depok or TMP Surabaya. The origin is recorded on every AWB in the batch, which is what lets a return later find its own way home without anyone looking it up. Check the preview: every row error shows before anything is committed.

    Where: Order creation → download upload.xlsx + links.csv

  3. 03

    Upload that file into Ninja Van

    DE / Implant

    The generated upload.xlsx goes into Ninja’s own order creation. This tool does not talk to Ninja directly — this step is a person moving a file. Nothing changed here afterwards changes the order on Ninja’s side.

    Where: Ninja Van’s order-creation system.

  4. 04

    Driver opens the link and files proof

    Driver — no login

    The link is opened only when some form of return happens at the point of delivery — normal proof-of-delivery and failed deliveries stay in the Ninja driver app, untouched. The driver enters their Driver ID and Hub Name (with a “my hub isn’t listed” fallback), then picks one of three: tidak ada retur (one confirm, no photos), retur sebagian or retur semua. A reject captures the Delivery Note twice (full page + return close-up), the goods, the AWB label, and how many pieces came back. The final screen says to screenshot it and inform the Station IC.

    Where: the /c/… link. Any phone, no account. Tidak ada retur → finished here.

  5. 05

    Validator checks the photos

    Validator

    Every reject — partial or whole — is reviewed before it moves. The Validator confirms the Delivery Note, the return section and the goods photos actually show what the driver claimed. Bad evidence is caught here rather than discovered three steps later.

    Where: Reject returns → Pending Validator

  6. 06

    DE uploads to Ninja

    DE / Implant

    What DE does depends on how much came back, and the app only offers the correct one.

    Retur sebagian — part came back

    The forward AWB is already completed, so a new return AWB is required. DE exports the return OC — origin pre-filled from the original order — uploads it to Ninja, and the row moves to Pending Print.

    Retur semua — the whole delivery refused

    No new AWB. The parcel already has one, so Ninja triggers RTS on the original forward tracking number. Validated rows are marked in bulk and exported for upload. This branch never reaches Pending Print — it travels on its original label.

    Where: Reject returns → Pending DE upload. Monitored to a 22:00 cutoff.

  7. 07

    Station IC prints, labels and repacks

    Station IC

    Partial returns only. IC filters the worklist by Hub Name, opens each row, finds the tracking number in OPV2, prints the label, labels and repacks the parcel, then sends it back. The tracking number is handed to them — no hunting through a chat group for it.

    Where: Reject returns → Pending Print → Printed & Labelled

  8. 08

    Final check before handover

    DE / ImplantClosed

    The returned goods arrive back and are checked once more immediately before handover to SwipeRx. The piece count the driver entered at the door is what this is checked against, alongside the goods photo and the notes on the BA Retur — three independent records of the same thing.

    Where: Reject returns → closed, with the full trail exportable to CSV.

Getting access

How to get in

Access is granted per person by the superadmin. Signing in with a valid work email is not enough on its own — the account has to be registered first.

If you need access

  1. Send the superadmin your Ninja Van Google work email and your full name.
  2. Say which part of the job you do — order creation, station, or oversight. That decides your role.
  3. Wait for confirmation that you've been registered.
  4. Open the address at the top of this page and sign in with that same Google account.
If sign-in bounces

You may hit a Ninja Van platform sign-in screen first — that's expected. If you get in but land on "No access to this page", your account exists but has no role yet. Go back to the superadmin.

If you are the superadmin

  1. Open Users in the top menu — only you can see it.
  2. Under Register a user, enter their Google email and name.
  3. Pick one or more roles. Hover any role to see exactly what it opens.
  4. Press Register. They can sign in immediately.
  5. To change someone later, use Edit roles, or Deactivate to revoke access without deleting them.
Worth knowing

A role change only takes effect the next time that person signs in — roles are baked into their session. Ask them to sign out and back in.

Drivers are not users

Couriers never get an account. The link itself is the credential — whoever holds it can file that delivery, and nothing else. That is why the links are long and random, and why they should not be posted anywhere public.

Doing the work

Step by step, per task

Create a day's orders DE / Implant

  1. Open Order creation.
  2. Choose the service — you pick it by name; shipper and branch fill in automatically.
  3. Choose one pickup date — the day Ninja collects from the warehouse. A single day, not a range.
  4. Attach the TMP .xlsx and read the preview: AWB count, total koli, and any row errors.
  5. Fix errors in the source file and re-attach before committing. If any row fails, nothing is created — it's all or nothing.
  6. Press Create, then download both files: the Ninja upload and the link map. They are named by service and creation time, e.g. Regular-B2BR-upload_20260819-1430.xlsx, so they stay sortable once they leave the browser.
  7. Upload the Ninja file into Ninja Van's system.

Find a courier link DE / ImplantStation IC

  1. Open Courier links.
  2. Search by AWB, pharmacy, or city.
  3. Copy the link and send it to the driver.

Use this when a driver says the link in their delivery instructions won't open, or the instruction text was cut off in print.

Work the reject queue ValidatorDE / ImplantStation IC

  1. Validator — open Pending Validator, check the photos (DN, return table, goods, labels) against what the driver claimed, select the good rows and press Validate. Nothing moves before this.
  2. DE, partial returns — on Pending DE upload, press Export return OC (one -R01 row per reject, origin pre-filled), upload it to Ninja, then Mark OC uploaded.
  3. DE / Validator, whole refusals — same tab: Export RTS list and Mark RTS triggered. No new AWB, no print step.
  4. Station IC — on Pending print, find the -R01 in OPV2 (it is shown on the row), print, label, repack, then Mark printed & labelled.
  5. Rows under the Origin unknown filter must be bulk-set first — they are excluded from the OC export so a return can never ship to the wrong warehouse.
  6. Narrow the list any way you need: stage tabs, per-column filters (type / origin / hub), free-text search, and row checkboxes for bulk actions — they stack.

Build a link by hand DE / Implant

Manual link makes one courier link without a TMP file. The link it produces is real and fully working — the driver app treats it exactly like one made from a batch. Use it to trial a delivery before trusting the bulk path, and for any one-off order that has no template.

  1. Open Manual link and fill in the AWB, koli, pharmacy and PO lines.
  2. Press Create link.
  3. Copy each column value it gives you — A, D, AB, AC and the full R instruction string — into Ninja by hand.
  4. Use Open as courier to confirm the link loads before sending anyone.
  5. Delete the test row when finished, which frees the AWB number for reuse.
The driver's side

What happens at the door

The wizard takes a different route depending on what the driver reports, and only shows the steps that route needs. There is no login at any point.

Tidak ada retur

  • Driver ID and Hub Name first — a “hub saya tidak ada di daftar” tick opens free text if the list is missing theirs
  • One confirm — no photos at all
  • Reminder: complete the delivery in the Ninja driver app as usual

Retur sebagian

  • Delivery Note, full page — signed & stamped, with the attestation tick
  • Close-up of the Berita Acara Return table
  • How many pieces came back — a count, no item names
  • Photos of the rejected goods and each AWB label (multiple allowed)
  • Review, submit, screenshot the final page for the Station IC

Retur semua paket

  • Chosen up front — the whole consignment is refused
  • Same captures as a partial return
  • Downstream it closes by RTS on the original AWB — no new label

What moved OUT of this link

  • Pharmacy and receiver POD photos — Ninja driver app
  • Failed-delivery reporting — Ninja driver app
  • SP Manual collection — the physical document still travels with the RDO
Example photos

The Delivery Note and the DN return close-up each carry a “Lihat contoh foto” link showing the real document, so a driver unsure what to shoot can check. It is hidden by default and nothing downloads until it is tapped — steps with no example photo simply don’t show the link.

Surat Pesanan is no longer photographed here

Collecting SP Manual was removed from the driver link so a reject takes as little of the driver’s time as possible. The instruction still appears in the delivery instructions on the label, and the physical document still travels back with the RDO — it simply is not captured in the app.

Tell every driver this

Filing here does not replace confirming the delivery in the Ninja driver app. Both are required. If goods were returned, the driver should screenshot the final screen and tell their Station IC — that screen lists the AWBs coming back.

Tracking numbers

How an order is numbered

One SwipeAWB is one Ninja order — a single MPS bundle holding every parcel for that pharmacy visit. Getting this wrong is what breaks parcels in the driver app, so it is worth recognising a correct row on sight.

ColumnFieldValue
Arequested_tracking_numberThe SwipeAWB — e.g. AWB02U24V
Dmerchant_order_numberThe same SwipeAWB
ABtotal_quantityTotal koli across every PO in that AWB
ACrequested_piece_tracking_numbersOne per koli, prefixed by its own PO — e.g. PO1-01, PO1-02, PO2-03
WweightThe AWB total, not per parcel
Rdelivery_instructionsThe RDO wording, then one big tappable sentence — “Apabila ada retur, catat di Delivery Note dan buka link berikut: <URL>”
The rule

Each child piece is prefixed with the PO number that parcel belongs to, then a dash and a two-digit number. The numbering runs continuously across the whole AWB — it does not restart at each PO — so a PO with several koli shifts every number after it.

Why PO-prefixed

Ninja allows custom piece IDs, and the pieces still attach to their parent when the order is created from the manual template. Keeping the PO in the piece ID is what ties each returned piece back to the PO it belongs to.

Limits & troubleshooting

Known limits, stated plainly

These are current behaviours, not bugs to report. Knowing them saves a lot of guessing.

Re-uploading a corrected file does not correct anything

Any SwipeAWB that already exists is skipped, not updated. Fixes to an address, koli or weight will not be applied, and the AWB keeps its original link.

If every AWB in the file already exists, the upload is now refused outright with a message saying so. It used to report success and hand back a file containing only a header row — which looked fine and shipped nothing.

For now: use a different SwipeAWB, or ask for the record to be corrected directly.

Links printed before late July are dead

The app moved to a new address. Older links point at the retired one and will fail to open.

Fix: the link still works — insert .ninjavan after swiperx-operator in the address bar, or just look the AWB up under Courier links and copy the current link.

A wrong file is refused before it can commit

The TMP’s header row is checked before parsing — upload the wrong file (or a drifted layout) and Order creation refuses it with a message naming the offending cell, instead of silently committing weights as AWBs.

The delivery instruction is at its character limit

Column R is capped at 500 characters and the link is counted twice inside it. The compliance wording currently fits exactly, with nothing to spare. If you see a warning that the instruction was trimmed, do not use that row — raise it, because the legal wording will be incomplete.

Deleting an upload — allowed, until a driver touches it

An uploaded OC can now be deleted from Upload history, which frees every SwipeAWB in it — that is the correction path: delete the bad batch, upload the fixed file.

The moment any courier work exists on any AWB in the batch — a photo, a submitted result, a reject row — the delete is refused. Evidence a driver filed is never destroyed. Users are still deactivated rather than deleted.
